# Portfolio CMS and messaging

The connected Supabase project is `qizcujjcqzekzoneryxp`. Portfolio data is isolated in `portfolio_profiles`, `portfolio_content_records`, `portfolio_inquiries`, and two `portfolio_*_rate_limits` tables. The separate app's customer data and roles are not portfolio authorization records.

Apply `database/schema.sql`, `database/auth.sql`, and `database/auth-rate-limit.sql` when installing another project. This connected project also needs the reviewed `database/shared-auth.sql` patch: its customer Auth trigger requires a phone and full name. The patch skips new portfolio-only identities, preserves existing customer synchronization, and rejects unreviewed function revisions. It does not relax customer constraints or change the shared Auth Site URL.

Public project credentials are in `apps/web/lib/supabase-project.ts`, overridable with `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` or `NEXT_PUBLIC_SUPABASE_ANON_KEY`. They cannot assign roles. CMS calls validate the bearer token with `auth.getUser`, require email verification, and read the current protected portfolio role on every request. The user token stays attached to Data API requests so RLS remains enforced.

Register `safikasultana90@gmail.com` through `/register` and confirm the email. The database grants that identity `super_admin`. Open `/account`, then **Open content studio**, or visit `/admin`. Other registrations receive `viewer` and cannot edit content. Public clients and editors cannot assign roles. See [authentication setup](auth-setup.md) for callback configuration and login-function deployment.

The editor manages profile, skills, projects, experience, education, certifications, posts, and settings. Save drafts before publishing. Profile content can include a real `cvUrl`. Metrics require a dataset and methodology. Content is displayed as text. Editors can manage content and inquiry status; only administrators can alter settings or delete records.

Optional contact-form storage and the optional Nest API require `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and a random `CONTACT_RATE_LIMIT_SECRET` in their server environment. Never put a service key in `NEXT_PUBLIC_*`, source, or Git. The web app currently has no server key, so contact requests direct visitors to the supplied email instead of falsely confirming storage. The server checks same-origin requests, bounded validation, a process guard, and a service-only durable limit before storing a message. Enable `TRUST_PROXY=true` only behind a proxy that replaces client IP headers; Vercel is detected automatically.

Run `node --test apps/web/test/*.test.cjs database/test/*.test.cjs` after `npm ci`. Database tests cover role assignment, own-profile reads, published-only content, private inquiries, editor/admin boundaries, shared Auth compatibility, and rate limits. Service-only limiter tables intentionally have RLS with no client policies. Review Supabase advisors for the shared project; findings on the other app's functions belong to that app's review.
